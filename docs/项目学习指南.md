## 1. 项目全景：一条消息的旅程

在学任何具体细节之前，先建立整体感。当用户发送一条消息 `"我最近压力很大，总是失眠"` 时，系统经历以下过程：

```
用户发送 HTTP POST /api/v1/chat
        │
        ▼
   chat.py (API 层)
   ├─ 1. 加载历史记忆（从数据库）
   ├─ 2. 保存用户消息（到数据库）
   ├─ 3. 调用 run_workflow()
   │         │
   │         ▼
   │    LangGraph 工作流
   │    ├─ load_memory_node    → 初始化 state 字段
   │    ├─ classify_intent     → LLM 判断意图: "mental"
   │    ├─ mental_agent_node   → VLLM 生成回复
   │    └─ save_memory_node    → 更新轮次计数
   │         │
   │         ▼
   ├─ 4. 保存助手回复（到数据库）
   └─ 5. 返回 ChatResponse 给用户
```

**核心数据载体**：整个工作流共享一个字典对象 `AgentState`，所有节点通过读写这个字典来传递信息，不会直接互相调用。这是 LangGraph 的核心设计思想。

## 2. 配置系统 (`app/config.py`)

### 它解决什么问题？

硬编码配置（如 API Key、数据库地址）是危险且不灵活的。pydantic-settings 让我们把所有配置写在 `.env` 文件里，启动时自动读取和验证。

### 代码解读

```python
# app/config.py

from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    # 告诉 pydantic-settings 去读 .env 文件
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="ignore")

    # 每个字段对应 .env 里的一个环境变量，= 后面是默认值
    APP_NAME: str = "health-advisor"
    DEBUG: bool = False
    DEEPSEEK_API_KEY: str = ""
    POSTGRES_URL: str = "postgresql+asyncpg://postgres:postgres@localhost:5432/health_advisor"
    
    # 记忆系统参数
    SHORT_TERM_WINDOW: int = 10       # 短期记忆保留最近几条消息
    CONSOLIDATION_INTERVAL: int = 10  # 每隔几轮触发一次长期记忆整理
    LONG_TERM_TOP_K: int = 5          # 加载几条长期记忆
```

### 单例模式：为什么用 `lru_cache`？

```python
# app/config.py:50
from functools import lru_cache

@lru_cache  # ← 关键！第一次调用后缓存结果，后续调用直接返回缓存
def get_settings() -> Settings:
    return Settings()  # 只会执行一次 .env 文件读取
```

**错误用法** ❌：
```python
settings = Settings()  # 每次都重新读 .env，且无法在测试中覆盖
```

**正确用法** ✅：
```python
settings = get_settings()  # 全项目统一入口，测试时可 mock
```

### 学习要点

- `BaseSettings` 来自 `pydantic-settings` 库，不是 `pydantic`
- 字段类型会自动验证：`DEBUG=abc` 会报错，必须是 `true/false`
- `lru_cache` 是 Python 标准库里的装饰器，让函数只执行一次，结果永久缓存

## 3. 应用入口与生命周期 (`app/main.py`)

### Lifespan 机制

FastAPI 用 `lifespan` 上下文管理器来控制应用启动和关闭时的行为，比旧版的 `@app.on_event("startup")` 更现代：

```python
# app/main.py:21
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    # ── 启动阶段 ──────────────────────────────
    setup_logging()          # 初始化结构化日志
    await init_db()          # 连接 PostgreSQL，自动建表
    await init_redis()       # 连接 Redis（失败只报警告，不崩溃）
    
    yield  # ← 应用正常运行期间在这里"暂停"
    
    # ── 关闭阶段 ──────────────────────────────
    await close_redis()      # 关闭 Redis 连接
    await close_db()         # 释放数据库连接池
```

**为什么要手动关闭连接？**  
数据库连接池是系统级资源，不关闭会导致连接泄漏。`yield` 前后是一个完整的 try/finally 结构。

### 条件开放 API 文档

```python
# app/main.py:53
app = FastAPI(

    redoc_url="/redoc" if settings.DEBUG else None,

```

### 中间件叠加顺序

```python
# app/main.py:59

## 5. 认证系统 (`app/api/deps.py`)

### JWT 工作原理

JWT（JSON Web Token）是无状态认证方案：服务器不存 session，用签名验证 token 真实性。

```
登录流程：
用户名+密码 → 验证 → 生成 JWT → 返回给客户端
              
后续请求：
JWT → 服务器验签 → 解出 user_id → 查数据库 → 返回当前用户
```

### 代码实现

```python
# app/api/deps.py

# 签发 Token
def create_access_token(user_id: str) -> str:
    expire = datetime.now(timezone.utc) + timedelta(minutes=settings.JWT_EXPIRE_MINUTES)
    payload = {
        "sub": user_id,  # subject，存用户 ID
        "exp": expire,   # 过期时间，jwt 库自动验证
    }
    return jwt.encode(payload, settings.JWT_SECRET, algorithm=settings.JWT_ALGORITHM)

# 验证 Token
def decode_access_token(token: str) -> str:
    payload = jwt.decode(token, settings.JWT_SECRET, algorithms=[settings.JWT_ALGORITHM])
    user_id = payload.get("sub")
    return user_id  # 返回用户 ID 字符串
```

### REST vs WebSocket 认证差异

这是一个重要的架构决策：

```python
# REST 接口：Authorization: Bearer <token>
# app/api/deps.py:60
async def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(HTTPBearer()),
    ...
):
    user_id = decode_access_token(credentials.credentials)

# WebSocket：ws://host/ws/chat?token=<token>
# app/api/v1/chat.py:209
# WebSocket 协议规范不支持自定义 Header，只能用 URL 参数
token = ws.query_params.get("token")
user_id_str = decode_access_token(token)
```

**为什么 WebSocket 不能用 Header？**  
浏览器的 `WebSocket` API 不支持设置自定义请求头，这是协议层面的限制，不是 FastAPI 的问题。

## 6. LangGraph 工作流 (`app/core/workflow.py`)

### 什么是 LangGraph？

LangGraph 是在 LangChain 基础上构建的图编排框架。把 AI 工作流表达为一张**有向图**：节点是处理函数，边是数据流向，条件边是分支逻辑。

### AgentState：数据总线

```python
# app/core/state.py:8

class AgentState(TypedDict, total=False):
    # ── 输入 ──────────────────────────────
    user_id: str
    session_id: str
    messages: list[dict]               # [{"role": "user", "content": "..."}]
    
    # ── 意图识别结果 ──────────────────────
    intent: Literal["mental", "nutrition", "general"]
    intent_confidence: float
    
    # ── 记忆上下文 ────────────────────────
    short_term_memory: list[dict]      # 最近N条消息
    long_term_memory: list[dict]       # LLM整理的历史摘要
    user_profile: dict                 # 身高体重过敏原等
    
    # ── Agent 执行产物 ────────────────────
    tool_calls: list[dict]             # 工具调用记录
    rag_context: list[dict]            # ChromaDB 检索结果
    kg_context: list[dict]             # Neo4j 查询结果
    
    # ── 控制流 ────────────────────────────
    turn_count: int
    should_consolidate: bool           # 是否触发记忆整理
    
    # ── 输出 ──────────────────────────────
    response: str                      # 最终回复文本
```

`total=False` 的含义：TypedDict 默认所有字段必填，加这个参数后全变可选，节点只需处理自己关心的字段。

### 工作流图结构

```python
# app/core/workflow.py:118

def build_workflow():
    graph = StateGraph(AgentState)
    
    # 注册所有节点
    graph.add_node("load_memory", load_memory_node)
    graph.add_node("classify_intent", classify_intent_node)
    graph.add_node("mental_agent", mental_agent_node)
    graph.add_node("nutrition_agent", nutrition_agent_node)
    graph.add_node("general_agent", general_agent_node)
    graph.add_node("save_memory", save_memory_node)
    graph.add_node("consolidate_memory", consolidate_memory_node)
    
    # 设置入口
    graph.set_entry_point("load_memory")
    
    # 普通边：总是执行
    graph.add_edge("load_memory", "classify_intent")
    
    # 条件边：根据意图分叉到不同 Agent
    graph.add_conditional_edges(
        "classify_intent",       # 从哪个节点出发
        route_by_intent,         # 路由函数：读 state["intent"] 返回字符串
        {                        # 字符串 → 节点名称 映射
            "mental": "mental_agent",
            "nutrition": "nutrition_agent",
            "general": "general_agent",
        }
    )
    
    # 三个 Agent 完成后都汇入 save_memory
    for agent in ["mental_agent", "nutrition_agent", "general_agent"]:
        graph.add_edge(agent, "save_memory")
    
    # 条件边：是否触发记忆整理
    graph.add_conditional_edges(
        "save_memory",
        should_consolidate,      # 路由函数：读 state["should_consolidate"] 返回 bool
        {True: "consolidate_memory", False: END}
    )
    
    graph.add_edge("consolidate_memory", END)
    return graph
```

流程图示意：

```
load_memory
    │
    ▼
classify_intent
    │
    ├─── mental ───→ mental_agent ───┐
    ├─── nutrition → nutrition_agent ─┤──→ save_memory ──→ [consolidate?] ──→ END
    └─── general ──→ general_agent ──┘
```

### 懒加载单例

## 7. 意图识别 (`app/core/intent_router.py`)

### 核心思路

用 LLM 来做文本分类，让模型判断用户的问题属于心理、营养还是通用健康。比传统关键词匹配更灵活，能理解语义。

### Prompt 设计

```python
# app/prompts/intent_prompts.py:4

INTENT_CLASSIFICATION_PROMPT = """你是一个意图分类器...

## 类别定义
1. mental    — 情绪/压力/睡眠/人际关系/自我认知
2. nutrition — 饮食/菜谱/BMI/热量/特殊饮食
3. general   — 运动/疾病科普/养生/用药/体检（兜底类）

## 分类规则
- 同时涉及多类别时，选最核心的意图
- "失眠"侧重情绪原因 → mental；问助眠食物 → nutrition
- 不确定时倾向 general（兜底）

请返回 JSON: {"intent": "...", "confidence": 0.0-1.0, "reasoning": "..."}
"""
```

### 置信度兜底机制

```python
# app/core/intent_router.py:44

CONFIDENCE_THRESHOLD = 0.7

async def classify_intent(message, context="无"):
    result = await llm.complete_json(messages=..., temperature=0.1)  # 低温度 → 更稳定
    
    intent = result.get("intent", "general")
    confidence = float(result.get("confidence", 0.5))
    
    # 验证合法性
    if intent not in {"mental", "nutrition", "general"}:
        intent = "general"
    
    # 置信度不足 → 兜底
    if confidence < CONFIDENCE_THRESHOLD:
        # LLM 自己不确定，就不要乱路由，统一给通用 Agent
        intent = "general"
    
    return intent, confidence, reasoning
```

**为什么 temperature 设 0.1？**  
分类任务要稳定性，不需要创造性。低温度让模型每次输出几乎相同的结果。

### 节点包装

```python
# app/core/intent_router.py:66

async def classify_intent_node(state: AgentState) -> AgentState:
    """将 classify_intent 函数包装成 LangGraph 节点"""
    
    # 从 state 提取最新用户消息
    user_message = ""
    for msg in reversed(state.get("messages", [])):
        if msg.get("role") == "user":
            user_message = msg.get("content", "")
            break
    
    # 用最近6条记忆（3轮对话）作为上下文，帮助判断意图
    memory = state.get("short_term_memory", [])
    context = "\n".join([
        f"{'用户' if m['role']=='user' else '助手'}: {m['content'][:100]}"
        for m in memory[-6:]
    ]) if memory else "无"
    
    intent, confidence, _ = await classify_intent(user_message, context)
    
    # 写回 state（其他节点可以读到）
    state["intent"] = intent
    state["intent_confidence"] = confidence
    return state
```

## 8. LLM 客户端 (`app/llm/client.py`)

### 双后端设计

项目支持两个 LLM 后端，统一用 OpenAI SDK 调用（因为 DeepSeek 和 VLLM 都兼容 OpenAI API 格式）：

class LLMClient:

        )
        # 后端2：本地 VLLM 部署的微调模型（心理咨询专用）
        self._vllm = AsyncOpenAI(
            api_key="EMPTY",                      # VLLM 不验证 key，随便填
            base_url=settings.VLLM_BASE_URL,      # http://localhost:8001/v1
        )
```

### 三个核心方法

**① `complete()` — 一次性完整调用**

```python
async def complete(self, messages, model=None, backend="general", 
                   temperature=0.7, max_tokens=2048) -> LLMResponse:
    client = self._vllm if backend == "vllm" else self._general
    resp = await client.chat.completions.create(
        model=model_name,
        messages=messages,
        temperature=temperature,
        max_tokens=max_tokens,
    )
    return LLMResponse(
        content=resp.choices[0].message.content,
        model=model_name,
        usage={"prompt_tokens": ..., "completion_tokens": ...},
    )
```

**② `stream()` — 流式输出（逐 token）**

```python
async def stream(self, messages, ...) -> AsyncGenerator[str, None]:
    stream = await client.chat.completions.create(..., stream=True)
    async for chunk in stream:
        delta = chunk.choices[0].delta
        if delta and delta.content:
            yield delta.content  # 每次 yield 一小片文字
```

流式输出用于 WebSocket，让用户看到"打字机效果"，而不是等全部生成完再显示。

**③ `complete_json()` — 结构化 JSON 输出**

```python
async def complete_json(self, messages, ...) -> dict:
    resp = await self.complete(
        ...,
        response_format={"type": "json_object"},  # 强制 JSON 格式
    )
    try:
        return json.loads(resp.content)
    except json.JSONDecodeError:
        # 容错：有时 LLM 会在 JSON 外面包 markdown 代码块
        # ```json
        # {"intent": "mental"}
        # ```
        # 需要把 ``` 剥掉再解析
        content = resp.content.strip()
        if content.startswith("```"):
            lines = content.split("\n")

### NutritionAgent — Plan-Execute 模式

这是最复杂的 Agent，采用"先规划，再执行，再综合"的三步流程。

**Step 1 — Plan（规划）**

```python
# app/agents/nutrition_agent.py:56

async def _plan(self, state) -> list[dict]:
    """让 LLM 分析用户需求，拆解成子任务列表"""
    
    # 提示 LLM 可用的工具
    prompt = """可用工具:
    1. calculate_health — 计算 BMI/BMR/TDEE
    2. search_recipes   — 检索菜谱
    3. query_knowledge  — 查询营养知识图谱
    4. direct_answer    — 直接回答，无需工具
    
    用户: 推荐几道适合减脂的低热量晚餐
    
    返回 JSON: {"tasks": [{"type": "search_recipes", "params": {"query": "减脂低热量晚餐"}, "reason": "..."}, ...]}
    """
    
    result = await self.llm.complete_json(messages=[{"role": "user", "content": prompt}])
    return result.get("tasks", [])
    # 结果示例: [
    #   {"type": "search_recipes", "params": {"query": "减脂晚餐"}},
    #   {"type": "calculate_health", "params": {}}
    # ]
```

**Step 2 — Execute（并行执行）**

```python
# app/agents/nutrition_agent.py:133

async def _execute_all(self, tasks, state) -> list[dict]:
    """用 asyncio.gather 并行执行所有子任务"""
    executable = [t for t in tasks if t.get("type") != "direct_answer"]
    
    results = await asyncio.gather(
        *[self._execute_task(t, state) for t in executable],
        return_exceptions=True,  # 某个任务失败不影响其他任务
    )
    # 过滤掉失败的任务
    return [r for r in results if not isinstance(r, Exception)]
```

**为什么用 `asyncio.gather`？**  
如果串行执行，搜索菜谱 300ms + 查知识图谱 200ms = 总共 500ms。并行执行只需 max(300ms, 200ms) = 300ms。

**Step 3 — Synthesize（综合）**

```python
# app/agents/nutrition_agent.py:184

async def run(self, state):
    tasks = await self._plan(state)             # 规划
    task_results = await self._execute_all(tasks, state)  # 执行
    
    # 分类结果
    rag_context = [r["result"] for r in task_results if r["type"] == "search_recipes"]
    tool_results = [r for r in task_results if r["type"] == "calculate_health"]
    
    # 把所有结果注入 prompt，让 LLM 综合回答
    messages = build_nutrition_messages(
        user_message=user_message,
        rag_context=rag_context,    # 检索到的菜谱
        tool_results=tool_results,  # BMI/TDEE 计算值
        user_profile=...,
    )
    
    resp = await self.llm.complete(messages=messages, backend="general")
    state["response"] = resp.content
    return state
```

## 11. 记忆系统 (`app/memory/`)

### 为什么需要记忆？

LLM 是无状态的，每次调用都是独立的。记忆系统让 AI 能记住用户说过的话。

### 两种记忆类型

```
短期记忆（Short-Term）：当前会话最近 N 条消息
    → 存在 messages 表
    → 每次对话都加载
    → 提供对话连续性

长期记忆（Long-Term）：跨会话的 LLM 摘要
    → 存在 long_term_memories 表
    → 每 10 轮整理一次
    → 提供跨会话记忆
```

### MemoryManager — 加载与保存

```python
# app/memory/manager.py

class MemoryManager:
    
    async def load_short_term(self, db, session_id) -> list[dict]:
        """取最近 SHORT_TERM_WINDOW(=10) 条消息"""
        result = await db.execute(
            select(Message)
            .where(Message.session_id == session_id)
            .order_by(Message.created_at.desc())  # 最新的排在前面
            .limit(window)
        )
        messages = result.scalars().all()
        # 反转：让最旧的消息排在前面（符合对话顺序）
        return [{"role": m.role, "content": m.content} for m in reversed(messages)]
    
    async def load_long_term(self, db, user_id) -> list[dict]:
        """取最近 LONG_TERM_TOP_K(=5) 条跨会话摘要"""
        result = await db.execute(
            select(LongTermMemory)
            .where(LongTermMemory.user_id == user_id)
            .order_by(LongTermMemory.created_at.desc())
            .limit(top_k)
        )
        # 返回格式：[{"summary": "...", "key_topics": [...], "emotional_state": "..."}]
    
    async def save_long_term(self, db, user_id, summary, key_topics, ...):
        """整理后的摘要持久化"""
        memory = LongTermMemory(user_id=user_id, summary=summary, ...)
        db.add(memory)
        await db.flush()
```

## 12. RAG 检索层 (`app/rag/`)

RAG = Retrieval-Augmented Generation（检索增强生成）：先检索相关文档，再把文档内容注入 prompt，让 LLM 基于真实数据回答。

### 向量嵌入 (`embedder.py`)

```python
# app/rag/embedder.py

MODEL_NAME = "BAAI/bge-small-zh-v1.5"  # 中文小模型，512维，~90MB，首次自动下载

@lru_cache(maxsize=1)  # 模型很重，只加载一次
def _load_model():
    return SentenceTransformer(MODEL_NAME)

def embed_text(text: str) -> list[float]:
    model = _load_model()
    # normalize_embeddings=True：归一化后余弦相似度等于点积，查询更快
    return model.encode(text, normalize_embeddings=True).tolist()
    # 返回 512 个浮点数的列表，代表文本的语义向量
```

**什么是向量？** 把文字变成数字列表，语义相近的文字向量距离更近。"减脂晚餐"和"低热量晚餐"的向量比"心情低落"的向量更接近。

# 图谱结构：
# (:Food {name:"菠菜"}) -[:CONTAINS {amount:"2.7mg"}]-> (:Nutrient {name:"铁"})
# (:Food {name:"菠菜"}) -[:BENEFITS]-> (:Condition {name:"贫血"})

async def query_nutrition_knowledge(entity, max_hops=2):
    # 一跳查询：直接相关节点
    one_hop = await run_query("""
        MATCH (n)-[r]->(m)
        WHERE toLower(n.name) CONTAINS toLower($entity)
        RETURN n.name, type(r), m.name, properties(r)
        LIMIT 20
    """, {"entity": entity})
    # 查"菠菜" → [("菠菜", "CONTAINS", "铁"), ("菠菜", "BENEFITS", "贫血")]
    
    # 结果不足3条 → 扩展到二跳
    if len(one_hop) < 3 and max_hops >= 2:
        two_hop = await run_query("""
            MATCH (n)-[r1]->(mid)-[r2]->(m)
            WHERE toLower(n.name) CONTAINS toLower($entity)
            RETURN n.name, type(r1)+'->'+mid.name+'->'+type(r2), m.name
            LIMIT 10
        """, {"entity": entity})
        # 查"菠菜" → [("菠菜", "CONTAINS->铁->TREATS", "贫血")]
    
    # 关系类型翻译成中文
    return [{"entity": "菠菜", "relation": "含有", "target": "铁", "extra": {"amount": "2.7 mg"}}]

       │   │   └─ 返回: [蒸红薯(0.89), 豆腐海带汤(0.82), 凉拌黄瓜(0.79), ...]
       │   │
       │   └─ calculate_health({})
       │       ├─ 从 user_profile 获取: weight=70, height=175, age=30, gender="male"
       │       ├─ calculate_bmi(70, 175) → BMI:22.9, "正常"
       │       ├─ calculate_bmr(70, 175, 30, "male") → 1703 kcal
       │       └─ calculate_tdee(..., "moderate") → 2640 kcal
       │
       ├─ 更新 state: rag_context=[菜谱列表], tool_calls=[健康指标]
       │
       └─ Step3: Synthesize
           ├─ build_nutrition_messages(
           │     user_profile={...},    # Layer2: 画像
           │     short_term_memory=[...], # Layer3: 历史
           │     rag_context=[蒸红薯...], # Layer4: 检索结果
           │     tool_results=[BMI...]    # Layer5: 计算结果
           │   )
           └─ llm.complete(messages, backend="general") → 综合回复文本

④ chat.py 续
   ├─ _save_message(role="assistant")  → 存助手回复到 DB
   ├─ session.turn_count += 1          → 更新轮次
   ├─ 判断 should_consolidate:
   │   └─ turn_count % 10 == 0？→ 触发记忆整理
   └─ 返回 ChatResponse {
           session_id, intent:"nutrition", confidence:0.93,
           response:"根据您的档案（BMI 22.9，TDEE 2640 kcal）...",
           tool_calls:[{tool:"health_calc", result:{bmi:22.9,...}}],
           metadata:{latency_ms:1240, turn_count:5}
         }

⑤ RequestLoggingMiddleware 记录: POST /api/v1/chat 200 1240ms
```

### WebSocket 流式请求

WebSocket 与 REST 的主要差异：

```
① 建立连接: ws://host/api/v1/ws/chat?token=<jwt>
   └─ 认证通过 → 进入消息循环

② 每次收到消息:
   ├─ 意图识别完成 → 立即推送: {"type":"intent","data":{"intent":"nutrition"}}
   ├─ 工具执行中   → 立即推送: {"type":"tool","data":{"tool":"planner","status":"running"}}
   ├─ 每个 token   → 立即推送: {"type":"token","data":{"content":"根"}}
   │                           {"type":"token","data":{"content":"据"}}
   │                           ...（打字机效果）
   └─ 完成        → 推送: {"type":"done","data":{"session_id":"...","latency_ms":1100}}

③ 用户断开 → WebSocketDisconnect 异常 → 正常退出循环
```

## 第十六节：Phase 4 — 模型微调全流程（QLoRA）

### 背景与目标

心理咨询 Agent（`MentalAgent`）使用本地部署的细调模型，而非通用 DeepSeek API。原因：
- 心理健康对话需要特定语气和危机识别能力，通用模型效果有限
- 敏感对话不适合上传至第三方 API
- RTX 3060 6GB 可以用 4-bit QLoRA 微调 3B 参数模型

### 数据准备（SoulChat 格式转换）

原始数据来自 SoulChat 数据集（中文心理健康对话），需要转换为 LlamaFactory ShareGPT 格式：

```python
# scripts/data_soulchat.py 输出格式
{
  "conversations": [
    {"from": "human", "value": "用户说的话"},
    {"from": "gpt",   "value": "治疗师的回复"}
  ],
  "system": "你是一名专业的心理健康顾问..."
}
```

**关键字段名**：LlamaFactory 默认期望 `conversations`（消息列表）+ `from`/`value`（角色/内容键），这些均可通过 `dataset_info.json` 配置覆盖。

### dataset_info.json 配置详解

```json
{
  "mental_health_sft": {
    "file_name": "mental_health_sft.json",
    "formatting": "sharegpt",
    "columns": {
      "messages": "conversations",
      "system": "system"
    },
    "tags": {
      "role_tag": "from",
      "content_tag": "value",
      "user_tag": "human",
      "assistant_tag": "gpt"
    }
  }
}
```

**注意**：`columns` 里的 `system` 字段和 `tags` 里的 `system_tag` 是**两个不同的东西**：
- `columns.system`：指定数据集中哪个字段是 system prompt（列名映射）
- `tags.system_tag`：指定 conversations 列表里哪个 `from` 值代表 system 角色（默认 `"system"`）

不要在 `tags` 里重复声明 `system_tag`，否则 LlamaFactory 内部逻辑会产生冲突。

### 训练配置（train/deepseek_8b_qlora.yaml）

```yaml
model_name_or_path: Qwen/Qwen2.5-3B-Instruct   # 基础模型（实际使用 3B，命名沿用原始）
finetuning_type: lora
quantization_bit: 4                              # 4-bit QLoRA，显存从 ~6GB 降至 ~2GB

lora_rank: 32
lora_alpha: 64
lora_dropout: 0.05
lora_target: all                                 # 对所有线性层应用 LoRA

per_device_train_batch_size: 1
gradient_accumulation_steps: 16                  # 等效 batch_size = 16
cutoff_len: 1024                                 # 最大序列长度

dataset: mental_health_sft
dataset_dir: data/training
output_dir: outputs/mental_health_lora
```

**为什么 gradient_accumulation_steps=16**：显卡显存不足以放大 batch，通过累积 16 个小 batch 的梯度再更新，模拟大 batch 效果。

### 绕过 CLI 直接调用 Python API

LlamaFactory CLI（`llamafactory-cli train`）在 Windows 上有时静默退出（exit code 非 0 但无错误信息），原因是：

## 第十七节：环境配置踩坑记录（2026-05-07）

> 记录首次在 Windows RTX 3060 环境下配置 QLoRA 训练全流程中遇到的问题，每个问题附原因和解决方法。

### 问题 1：conda 环境在 C 盘，无法移动（权限）

**现象**：`conda create --clone langgraph --prefix D:\anaconda3\envs\langgraph` 报 `PermissionError`

**原因**：Anaconda 安装在 D 盘但以管理员权限安装，当前用户对 `D:\anaconda3\envs` 没有写权限。

**解决**：以管理员身份运行终端后重新克隆，克隆成功后用 `icacls` 赋权：
```cmd
icacls "D:\anaconda3\envs\langgraph" /grant %USERNAME%:(OI)(CI)F /T
```
注意：`/grant BLUE:(OI)(CI)F` 会失败（用户名含特殊字符或大小写），改用 `%USERNAME%` 环境变量。

**教训**：`icacls` 用户名参数对大小写和空格敏感，优先用 `%USERNAME%` 代替硬编码用户名。

### 问题 2：误删新环境（conda env remove 解析错误）

**现象**：克隆到 D 盘后运行 `conda env remove -n langgraph`，结果删掉了 D 盘新环境而非 C 盘原版。

**原因**：`-n langgraph` 查找的是 conda 环境名，D 盘版本的名字也叫 `langgraph`（克隆时继承了名字），且排在搜索路径前面。

**解决**：重新克隆一次。

**教训**：要删除特定路径的环境，用 `--prefix` 而非 `-n`：
```cmd
conda env remove --prefix "D:\anaconda3\envs\langgraph"
```

### 问题 3：PyTorch CUDA 版本未安装（仅有 CPU 版）

**现象**：`python -c "import torch; print(torch.cuda.is_available())"` 输出 `False`，torch 版本为 `2.11.0+cpu`。

**原因**：默认 `pip install torch` 安装的是 CPU 版。

**解决**：
```cmd
pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124
```
CUDA 12.4 对应 `cu124`，与 nvidia-smi 显示的驱动版本需匹配（CUDA 驱动 ≥ 12.4 即可）。

### 问题 4：torchaudio 版本与 torch 不匹配（DLL 崩溃）

**现象**：`import torchaudio` 报 `OSError: [WinError 127] 找不到指定的程序`，训练时 CLI 静默退出。

**原因**：重新安装 torch 2.6.0+cu124 后，torchaudio 仍是原来的 2.11.0（CPU 版），两者 ABI 不兼容，DLL 加载失败。

**解决**：
```cmd
pip install torchaudio==2.6.0 --index-url https://download.pytorch.org/whl/cu124
```

**教训**：torch/torchvision/torchaudio **三件套版本必须一致**，更新其中一个时其他两个也要同步更新。

### 问题 5：pip 安装到用户目录而非 conda 环境

**现象**：`pip install` 时提示 `Defaulting to user installation because normal site-packages is not writeable`，包安装到 `C:\Users\BLUE\AppData\Roaming\Python\Python311\site-packages` 而非 conda 环境。

**原因**：`D:\anaconda3\envs\langgraph\Lib\site-packages` 没有写权限（管理员安装）。

**解决**：先用 `icacls` 赋权，再重新 pip install：
```cmd
icacls "D:\anaconda3\envs\langgraph" /grant %USERNAME%:(OI)(CI)F /T
pip install --upgrade <package>
```
验证：`pip show <package>` 看 Location 字段，应为 conda env 路径。

**注意**：Python 用户目录的包（`AppData\Roaming\Python`）优先级高于 conda env，两处都有同一包时以用户目录版本为准，可能造成版本混乱。

### 问题 6：HuggingFace 缓存写入 C 盘

**现象**：设置了 `setx HF_HOME=D:\hf_cache\huggingface` 但模型仍下载到 C 盘。

**两个原因**：
1. `setx` 只对**新开**的终端生效，当前 session 需要额外 `set HF_HOME=...`
2. `D:\hf_cache` 目录没有写权限

**解决**：
```cmd
set HF_HOME=D:\hf_cache\huggingface
set HF_DATASETS_CACHE=D:\hf_cache\huggingface\datasets
icacls "D:\hf_cache" /grant %USERNAME%:(OI)(CI)F /T
```

**教训**：`setx` = 永久写注册表；`set` = 当前 session。新开终端前两者效果相同，新开终端后只有 `setx` 的值生效。

### 问题 7：HF_ENDPOINT 尾部空格导致 DNS 失败

**现象**：`set HF_ENDPOINT=https://hf-mirror.com ` （尾部有空格），下载时报 `hf-mirror.com%20` 域名解析失败。

**原因**：Windows `set` 命令不会自动 trim 空格，`%20` 是空格的 URL 编码。

**解决**：重新设置，确保无尾部空格：
```cmd
set HF_ENDPOINT=https://hf-mirror.com
```

### 问题 8：LlamaFactory 训练静默退出

**现象**：`llamafactory-cli train train/deepseek_8b_qlora.yaml` 瞬间退出，无任何输出或错误信息。

**根本原因（两层）**：
1. **DLL 崩溃**：torchaudio 版本不匹配，C 层崩溃不触发 Python 异常处理器
2. **Windows multiprocessing**：DataLoader 用 `spawn` 模式，子进程会重新 import 主模块，必须有 `if __name__ == "__main__"` 守卫，否则子进程无限递归

**解决**：创建 `run_train.py`，在 Python 层调用 `run_exp()`，绕过 CLI 入口点，并加上完整的异常捕获和 `if __name__ == "__main__"` 守卫（见第十六节）。

### 问题 9：dataset_info.json 配置导致 0 条样本

**现象**：训练日志显示 `"Dropped invalid example: []"`，数据集加载后为空。

**原因**：
1. `dataset_info.json` 同时在 `columns` 里写了 `"system": "system"` 又在 `tags` 里写了 `"system_tag": "system"`，LlamaFactory 的 `SharegptDatasetConverter` 在处理 system 时逻辑冲突
2. 引用了不存在的 `mental_health_eval.json`，导致数据集加载报错

**解决**：
- 从 `tags` 中删除 `system_tag` 字段（保留 `columns.system` 即可）
- 删除 `dataset_info.json` 中不存在文件的数据集条目

**原理**：`system_tag` 默认值是 `None`（不在 tags 里时），`columns.system` 负责从数据行中找 system 字段——两者职责不同，不要重复声明。

### 问题 10：torch 包物理位置与 xcopy 移动

**背景**：部分包在 conda env 赋权前安装到了用户目录，需要迁移到 conda env。

**方法**（管理员终端）：
```cmd
xcopy /E /I /Y "C:\Users\BLUE\AppData\Roaming\Python\Python311\site-packages\torch" "D:\anaconda3\envs\langgraph\Lib\site-packages\torch"

- 如果目标路径已有同名包（版本不同），会直接覆盖
- `.pth` 文件、`dist-info` 目录也需要一并迁移，否则 `pip show` 找不到包

## 第十八节：知识图谱 Neo4j 详解

### 为什么用图数据库？

关系型数据库（PostgreSQL）擅长存"表格型"数据，但营养学知识本质上是**网状关系**：

```
食物 → 含有 → 营养素 → 可缓解 → 疾病
食物 → 有益于 → 疾病
食物 → 禁忌于 → 疾病
```

如果用 SQL 表达 "菠菜对贫血有益，原因是含铁，铁可以缓解贫血" 这条两跳关系，需要 3 张表 + 2 次 JOIN。用 Cypher（Neo4j 查询语言）只需一行：

```cypher
MATCH (f:Food)-[:CONTAINS]->(n:Nutrient)-[:TREATS]->(c:Condition)
WHERE f.name = '菠菜' AND c.name = '贫血'
RETURN f, n, c
```

图数据库把"关系"本身作为一等公民存储，多跳查询性能远优于 JOIN。

---

### 图谱 Schema

本项目的营养知识图谱包含三类节点和六种关系：

```
节点类型：
  (:Food)      — 食物    {name, aliases, calories_per_100g}
  (:Nutrient)  — 营养素  {name, unit, daily_recommended}
  (:Condition) — 疾病/状态 {name, description}

关系类型：
  (:Food)     -[:CONTAINS {amount, unit}]→ (:Nutrient)   食物含某营养素
  (:Food)     -[:BENEFITS]→              (:Condition)    食物有益于某状态
  (:Food)     -[:CONTRAINDICATED_FOR]→   (:Condition)    食物禁忌于某状态
  (:Nutrient) -[:TREATS]→                (:Condition)    营养素可缓解某状态
  (:Food)     -[:PAIRS_WITH]→            (:Food)         食物适合搭配
  (:Food)     -[:AVOID_WITH]→            (:Food)         食物不宜同食
```

内置种子数据（`app/rag/kg_retriever.py:seed_nutrition_kg`）：

| 类别 | 节点 |
|------|------|
| Food | 苹果、菠菜、鸡胸肉、豆腐、三文鱼、燕麦、苦瓜 |
| Nutrient | 维生素C、铁、蛋白质、Omega-3、膳食纤维、钙 |
| Condition | 糖尿病、高血压、贫血、肥胖、心血管疾病 |

### 异步客户端 (`app/db/neo4j_client.py`)

```python
# app/db/neo4j_client.py

from neo4j import AsyncDriver, AsyncGraphDatabase

_driver: AsyncDriver | None = None  # 全局单例

def get_driver() -> AsyncDriver:
    global _driver
    if _driver is None:
        cfg = get_settings()
        # bolt:// 协议：Neo4j 专有二进制协议，比 HTTP 更高效
        _driver = AsyncGraphDatabase.driver(
            cfg.NEO4J_URI,                          # bolt://localhost:7687
            auth=(cfg.NEO4J_USER, cfg.NEO4J_PASSWORD),  # 默认 neo4j/neo4j_password
        )
    return _driver

async def run_query(cypher: str, params: dict | None = None) -> list[dict]:
    driver = get_driver()
    async with driver.session() as session:   # session 管理连接生命周期
        result = await session.run(cypher, params or {})
        return await result.data()            # 返回 list[dict]，每个 dict 是一行记录
```

**单例驱动的意义**：Neo4j 驱动内部维护连接池，全局只需一个实例。每次查询通过 `driver.session()` 从池中获取连接，查询完自动归还。

**`.env` 配置对应关系**：

```
NEO4J_URI=bolt://localhost:7687       ← docker-compose ports: "7687:7687"
NEO4J_USER=neo4j
NEO4J_PASSWORD=neo4j_password         ← docker-compose NEO4J_AUTH: neo4j/neo4j_password
```

> ⚠️ 重启 Docker 容器后如遇认证失败，先确认 `.env` 中 `NEO4J_PASSWORD` 与 `docker-compose.yml` 的 `NEO4J_AUTH` 密码部分一致。

### 查询逻辑 (`app/rag/kg_retriever.py`)

核心函数 `query_nutrition_knowledge` 实现了自适应深度查询：

**一跳查询**（直接关联节点）

```python
# app/rag/kg_retriever.py:39

one_hop_cypher = """
MATCH (n)-[r]->(m)
WHERE toLower(n.name) CONTAINS toLower($entity)
   OR any(alias IN coalesce(n.aliases, []) WHERE toLower(alias) CONTAINS toLower($entity))
RETURN n.name AS entity, type(r) AS relation, m.name AS target,
       properties(r) AS rel_props, labels(m) AS target_labels
LIMIT 20
"""
```

逐句解读：

```
MATCH (n)-[r]->(m)               — 找任意节点 n，通过任意关系 r，指向节点 m
WHERE toLower(n.name)            — 节点名称（忽略大小写）
      CONTAINS toLower($entity)  — 包含查询词（模糊匹配，不要求精确）
   OR any(alias IN coalesce(...) — 或者别名列表中也包含查询词
RETURN n.name, type(r), m.name  — 返回：起点名 / 关系类型 / 终点名
       properties(r)             — 关系上的属性（如 amount: "2.7", unit: "mg"）
LIMIT 20                         — 最多返回 20 条，防止图爆炸
```

```python

### 数据初始化 (`seed_nutrition_kg`)

```python
# app/rag/kg_retriever.py:98

async def seed_nutrition_kg() -> None:
    # 先检查是否已有数据，避免重复写入
    count_result = await run_query("MATCH (n) RETURN count(n) AS cnt")
    if count_result and count_result[0].get("cnt", 0) > 0:
        return   # 已有数据，跳过

    # 一次性写入所有节点和关系（MERGE = 存在则跳过，不存在则创建）
    seed_cypher = """
    MERGE (apple:Food {name: '苹果'}) SET apple.calories_per_100g = 52
    MERGE (spinach:Food {name: '菠菜'}) ...
    
    MERGE (vitC:Nutrient {name: '维生素C'}) SET vitC.unit = 'mg'
    ...
    
    MERGE (spinach)-[:CONTAINS {amount: '2.7', unit: 'mg'}]->(iron)
    MERGE (spinach)-[:BENEFITS]->(anemia)
    ...
    """
    await run_query(seed_cypher)
```

**`MERGE` vs `CREATE` 的区别**：
- `CREATE` — 无论是否存在都新建，可能产生重复节点
- `MERGE` — 存在则匹配，不存在才创建；保证幂等性，多次执行结果相同

**触发时机**：`main.py` 的 lifespan 在应用启动时调用，容器重启后自动补数据：

```python
# app/main.py
try:
    from app.rag.kg_retriever import seed_nutrition_kg
    await seed_nutrition_kg()   # count=0 时写入，count>0 时直接返回
    await logger.ainfo("neo4j_ready")
except Exception as e:
    await logger.awarning("neo4j_seed_skipped", error=str(e))  # Neo4j 未启动时只告警，不崩溃
```

**扩充知识图谱**（添加新食物）

在 `seed_nutrition_kg` 的 `seed_cypher` 里追加 MERGE 语句，然后重启服务即可（因为 MERGE 是幂等的，已有节点不会重复创建）：

```cypher
-- 添加新食物：胡萝卜
MERGE (carrot:Food {name: '胡萝卜'})
  SET carrot.calories_per_100g = 41

MERGE (betaCarotene:Nutrient {name: 'β-胡萝卜素'}) SET betaCarotene.unit = 'μg'
MERGE (eyeHealth:Condition {name: '视力保护'})

MERGE (carrot)-[:CONTAINS {amount: '8285', unit: 'μg'}]->(betaCarotene)
MERGE (carrot)-[:BENEFITS]->(eyeHealth)
```
